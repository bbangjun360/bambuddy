# Purpose

Implement WP-040, the smallest ERP Draft Write baseline. A review-safe synthetic ERP
production request can create exactly one Draft ERP output document through the mock ERP
adapter, while Bambuddy remains the only print execution and printer-control system.

# Scope

In scope:

- Draft-only ERP write adapter/client against the deterministic mock ERP endpoint.
- Completion-event or draft-write input schema for an existing review-only
  `ErpProductionRequest`.
- Idempotent conversion of a review-safe source request into one synthetic Draft ERP
  output document.
- Local audit record of draft write attempts, statuses, ERP document identity, retryable
  failures, and safe failure messages.
- Retryable classification for 429, 500, and timeout.
- Safe handling for invalid payload and expired token/auth failure.
- Timeout-after-create lookup using the same idempotency key before any retry would
  create a duplicate.
- Dead-letter state for failed draft events.
- Reconciliation report that detects a deliberately injected mock mismatch.
- Tests proving no submit/posting, queue, printer-command, bed automation, Obico, or
  scheduler side effects.
- `Makefile` focused targets only if required for WP-040 tests.

Out of scope:

- ERP document submit, Stock Entry submit, inventory posting, accounting posting, tax
  invoice, production accounting close, and real ERPNext calls.
- Production ERP credentials, direct ERPNext database access, Frappe custom app work,
  real customer/order/printer data, and production secrets.
- Printer registration or commands, queue dispatch or auto-start, scheduler changes,
  PrintFlow behavior, bed automation state mutation, Obico behavior, Orca behavior, and
  frontend/UI changes.
- Work in any other worktree or Work Package.
- Merging the PR.

# Architecture Boundaries

- Bambuddy remains the central control plane and sole authority for printer
  state-changing commands.
- ERP Draft Write is an adapter-side Draft output only; it must not enqueue executable
  jobs or call printer, scheduler, bed automation, Obico, Bambu MQTT, FTPS, G-code, GPIO,
  serial, BLE, USB, or hardware network paths.
- ERP writes are idempotent and start as Draft (`docstatus=0` in the mock response).
- ERP timeout after a create request performs lookup by stable idempotency key instead
  of blind re-create.
- All fixtures and logs use synthetic SKUs, work orders, customers, event IDs, and
  tokens. Logs and metrics must not include secrets.
- New functionality is disabled by default with `FARM_ERP_DRAFT_POSTING_ENABLED=false`.

# Decisions

- Treat the Work Package text and direct user request as the approved design for this
  turn; no additional product design document is created.
- Do not start harness services until `.env.harness` is WP-040-isolated.
- Reuse WP-030's additive backend structure and mock-service harness rather than adding a
  new service or production dependency.
- Store Draft Write audit data in a dedicated local table instead of `PrintLogEntry`,
  because WP-040 is not a print execution event and must not affect operator print
  history.
- Use Draft-only status names matching the user-suggested vocabulary unless existing
  code provides a narrower local convention.

# Failure and Recovery

- Duplicate draft attempts reuse the same local audit row and mock ERP document.
- Timeout after create records a retryable failure until lookup confirms the existing
  Draft document; confirmed lookup transitions to an idempotent success status.
- 429, 500, and timeout are retryable.
- Expired token/auth failure, invalid payload, and reconciliation mismatch are safely
  failed or dead-lettered without leaking tokens.
- Rollback is file-level removal of the WP-040 model/schema/service/route/tests, mock
  draft endpoints/scenarios, Makefile targets, and feature flag. If deployed, drop the
  additive draft-write audit table after confirming no finance review depends on it.

# Risks and Human Gates

- Any real ERPNext call, production credential, submit/posting behavior, printer command,
  queue mutation, bed mutation, Obico mutation, scheduler behavior, or UI change is scope
  creep and must stop this WP.
- A destructive database migration is not allowed in WP-040.
- If baseline failures are environmental or inherited, record exact evidence here before
  changing WP-040 code.
- No hardware canary exists for this WP; mock and local integration success is not
  evidence that physical or financial automation is safe.
- PR must remain unmerged.

# Outcomes

- WP-040 adds a default-off ERP Draft Write baseline controlled by
  `FARM_ERP_DRAFT_POSTING_ENABLED=false`.
- A review-safe `ErpProductionRequest` can create one local `ErpDraftWriteRecord` and
  one synthetic mock ERP Draft document with `docstatus=0`.
- Duplicate delivery for the same `event_uuid` is idempotent and does not create another
  local record or another mock ERP document.
- 429, 500, and timeout are classified retryable; timeout-after-create performs lookup by
  `farm_event_id` before any duplicate create.
- Expired token/auth failure and invalid payload are safe, non-retryable, and dead-lettered
  locally without leaking the synthetic token in details or logs.
- Reconciliation reports `MATCHED` for clean mock state and `MISMATCH` with
  `quantity_completed` for the injected mismatch scenario.
- Tests prove no `PrintQueueItem`, `PrintLogEntry`, or `BedAutomationCycle` rows are
  created and architecture tests prove WP-040 product files do not reference printer,
  queue, bed automation, Obico, scheduler, submit, inventory, or accounting paths.
- Bambuddy starts in the rebuilt WP-040 harness and `/health` returns healthy on port
  `18140`.
