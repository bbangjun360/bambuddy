# Purpose

Make the unchanged Bambuddy application start reliably in the local harness so developers can verify the app, PostgreSQL, logs, and mock services without real printer credentials.

# Scope

In scope:

- `.env.harness` with pinned local harness defaults and synthetic credentials.
- Makefile command contract for WP-000 validation targets.
- Harness smoke, reset, backup, restore, and persistence checks.
- Harness tests proving the command contract and isolation assumptions.
- Documentation of commands and observed evidence.

Out of scope:

- Orca, ERPNext, Obico, PrintFlow, bed automation, scheduler, costing, and UI changes.
- Real printer connections or production credentials.
- Changes to upstream Bambuddy routes, models, queue behavior, or UI.
- Git commits, pushes, merges, or farm-main modifications.

# Architecture Boundaries

Bambuddy remains the only state-changing control plane. The harness may start Bambuddy, PostgreSQL, and deterministic mock services only. No external module may connect to Bambu MQTT or FTPS, and no service may receive production printer credentials.

# Decisions

- Use synthetic harness credentials in a committed `.env.harness` because WP-000 requires clone-and-run defaults and no real secrets.
- Keep Bambuddy unchanged; all WP-000 behavior is harness and validation infrastructure.
- Use a small deterministic subset of upstream tests for `verify-fast`, then document the discovered broader suites.
- Keep reset confined by `COMPOSE_PROJECT_NAME=farm_harness` and a Makefile guard.

# Failure and Recovery

Rollback is file-level: remove WP-000 harness additions or restore previous Makefile and smoke script. Harness reset must run only with `COMPOSE_PROJECT_NAME=farm_harness` and must use Docker Compose project-scoped volumes. Backup and restore must use only the harness PostgreSQL service and generated files under `harness/artifacts/`, never production databases.

# Risks and Human Gates

- Docker daemon or BuildKit availability may be a human-only infrastructure blocker.
- Network access may be needed for image/package pulls during Docker build.
- No sudo or system package installation will be attempted without approval.
- No production credentials are needed or permitted.
