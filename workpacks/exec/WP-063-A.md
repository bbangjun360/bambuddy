# Purpose

Define and implement the safe dry-run boundary for a future Bambuddy-native
supervised plate-change command path.

# Current Behavior

Bambuddy already owns live printer command paths:

- `backend/app/services/bambu_mqtt.py` publishes live printer commands through
  `BambuMQTTClient.start_print()`, `stop_print()`, `pause_print()`,
  `resume_print()`, and the internal generic command emitter.
- `backend/app/services/printer_manager.py` owns active MQTT clients and wraps
  `start_print()` and `stop_print()`.
- `backend/app/api/routes/printers.py` exposes existing stop, pause, resume,
  bed-jog, home-axes, AMS load, and AMS unload controls.
- `backend/app/services/print_scheduler.py` and
  `backend/app/services/background_dispatch.py` upload over FTPS and then call
  `printer_manager.start_print()`.
- `backend/app/api/routes/print_queue.py` can stop an active queue item through
  `printer_manager.stop_print()` and can clear manual-start gates for scheduler
  dispatch.
- `backend/app/services/printflow_canary.py` blocks the prior PrintFlow server
  adapter model and provides a safe dry-run sentinel pattern.

No WP-063 route existed before this change. No checked-in WP-063 workpack file
was present, so WP-060 was read as the closest current plate-change correction
ExecPlan.

# Scope

In scope:

- Add default-off WP-063 config flags.
- Add a dry-run-only plate-change command service.
- Add enum-only schemas that reject extra command body fields.
- Add `POST /api/v1/plate-change/dry-run-commands`.
- Add `GET /api/v1/plate-change/status`.
- Add tests proving dry-run, approval, single-printer, no-command, and sentinel
  boundaries.
- Add WP-063 architecture and runbook docs.
- Add Make targets for focused WP-063 validation.

Out of scope:

- Real command execution.
- Any Bambu MQTT or FTPS call.
- Any printer credential, IP address, access code, or serial number.
- Scheduler, queue, background dispatch, ERP, Obico, or bed automation mutation.
- UI changes.
- Database migrations.
- General arbitrary command endpoint.

# Architecture Boundaries

Bambuddy remains the sole authority for future printer state-changing commands.
The WP-063-A dry-run route does not import or call live printer command modules.
The future real path should attach through a dedicated printer-manager method and
an allowlisted sequence id, not through PrintFlow, SwapMod, FTPS, queue dispatch,
scheduler dispatch, or arbitrary command text.

# Decisions

- The WP-063 route is separate from `printers.py` so it cannot accidentally call
  existing direct command helpers.
- Request schema uses `extra="forbid"`; arbitrary command body fields are
  rejected by validation.
- The only allowed `command_sequence` is `supervised_plate_change_v1`.
- The exact approval phrase is
  `CONFIRM_DRY_RUN_PLATE_CHANGE <printer-alias> <command-sequence>`.
- `GET /status` remains available while disabled so operators can inspect safe
  defaults without enabling the POST route.
- `FARM_PLATE_CHANGE_ALLOW_REAL_COMMANDS=true` blocks the POST route because real
  execution is not implemented in WP-063-A.

# Failure and Recovery

The dry-run service stores only in-memory audit records. Rollback is a file-level
revert with no migration or durable state cleanup. If the boundary ever returns a
non-zero sentinel, accepts extra command text, or calls a forbidden module, stop
and revert before any hardware canary.

# Risks and Human Gates

Remaining risks:

- Real command content is intentionally not reviewed or implemented.
- Existing Bambuddy internals still contain generic live command emitters for
  other features; WP-063 must not call them until a later Work Package adds a
  dedicated allowlisted executor and canary evidence.
- A physical canary requires a separate human checklist, emergency stop path,
  and sanitized one-printer approval record.
