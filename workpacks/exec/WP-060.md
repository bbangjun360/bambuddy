# WP-060-A PrintFlow Canary Readiness ExecPlan

# Purpose

Add default-off, dry-run PrintFlow canary readiness evidence without connecting
to real PrintFlow devices or authorizing real printer or bed motion.

# Current Behavior

The repository has no current WP-060 workpack file. The closest implemented
slice is WP-050 bed automation simulator, which keeps bed automation disabled
and dry-run by default. Existing mock services include `/printflow/v1/cycles`
for simulated bed-cycle behavior, but that endpoint is action-like and must not
be reused as a real canary control path.

Observed baseline on 2026-06-25 KST:

- `make verify-fast` passed before implementation.
- Existing WP-040, WP-050, and WP-070 patterns use additive config flags,
  mock adapters, focused architecture tests, harness tests, and Make targets.

# Scope

In scope:

- Default-off PrintFlow canary readiness flags.
- Dry-run and human-approval defaults.
- Mock-only readiness service and API.
- Harness-only readiness endpoints and sentinel counters.
- Tests proving no real printer, PrintFlow, queue, scheduler, ERP, Obico, or
  bed-cycle side effects.
- WP-060 runbooks and Trivy triage baseline documentation.

Out of scope:

- Real PrintFlow integration.
- Real printer canary execution.
- Queue dispatch or scheduler behavior.
- ERP submit, inventory, or accounting changes.
- Obico mutation.
- UI changes.
- Arbitrary G-code endpoints.
- Production credentials, real network endpoints, serials, access codes, or
  customer data.

# Architecture Boundaries

Bambuddy remains the control plane. WP-060-A only evaluates mock readiness and
records audit-only responses. It does not import printer managers, MQTT, FTPS,
queue models, schedulers, ERP clients, Obico action code, or bed automation
models. Any physical or uncertain state must remain blocked or manual-review
only and cannot start a next print.

# Decisions

- Use `printflow_canary` naming for WP-060 consistency.
- Keep backend readiness state in memory for WP-060-A. No database model or
  migration is needed for this readiness-only slice.
- Use mock scenario selection only; no real adapter URL or network client exists.
- Require explicit operator approval before the mock readiness probe is even
  evaluated.
- Keep the Trivy baseline under `docs/security/` and stage it explicitly because
  the repository ignores broad `security/` paths.

# Harness Changes

The harness mock service adds read-only readiness endpoints:

- `GET /printflow/v1/canary/readiness`
- `POST /printflow/v1/canary/readiness/check`

Scenarios include ready, heartbeat loss, camera unavailable, E-stop active,
motion timeout, lost reply, and object detected. Sentinel counters stay at zero
for forbidden side effects.

# Failure and Recovery

Invalid dry-run or audit-only requests fail before any mock probe. Missing human
approval returns an approval-required readiness result without probing. Duplicate
approved checks are idempotent by check key. Uncertain scenarios return blocked
or manual review and preserve zero side-effect sentinels.

Rollback is file removal only; there is no migration and no persistent WP-060
table.

# Risks and Human Gates

Physical canary work is not authorized by this plan. A later physical canary
requires named human approval, a canary printer/device checklist, visible stop
conditions, and evidence that no reachable high-risk security finding blocks
the run.
