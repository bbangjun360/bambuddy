# WP-060 Plate-Change Architecture Correction ExecPlan

## Purpose

Correct WP-060 after the PrintFlow/SwapMod clarification. PrintFlow and SwapMod
are treated as 3MF/G-code post-processing workflows, not remote control servers
that Bambuddy should call through `FARM_PRINTFLOW_BASE_URL`.

This correction must prevent anyone from attempting a fake PrintFlow server
canary. It does not authorize, execute, or add any real printer command.

## Current Behavior

The previous WP-060-B branch added a default-off `/real-canary-runs` route and a
server-adapter boundary based on a `FARM_PRINTFLOW_BASE_URL` and API token. That
assumption was incorrect because there is no PrintFlow server base URL.

Existing mock readiness checks under `/api/v1/printflow-canary/readiness-checks`
remain useful as dry-run, audit-only safety evidence. They do not move hardware,
call external services, enqueue jobs, or mutate ERP, Obico, or bed automation
records.

## Scope

In scope:

- Document the architecture correction.
- Add `docs/architecture/WP060_PLATE_CHANGE_ARCHITECTURE_CORRECTION.md`.
- Mark the legacy external adapter canary as deprecated/pending redesign.
- Keep `/real-canary-runs` blocked and auditable.
- Remove the live HTTP client behavior from the WP-060 external adapter path.
- Update runbooks so `FARM_PRINTFLOW_BASE_URL` is not presented as a live
  PrintFlow server setting.
- Add or update tests for safe defaults, no base URL requirement in default/test
  paths, no direct printer command path, no arbitrary G-code endpoint, and no
  queue or scheduler side effects.

Out of scope:

- Executing any real canary.
- Sending direct Bambu MQTT, FTPS, or G-code.
- Using printer IP addresses, access codes, serial numbers, or customer data.
- Implementing 3MF post-processing.
- Implementing Bambuddy-native plate-exchange commands.
- Queue auto-dispatch, scheduler behavior, ERP submit/posting, or Obico
  mutation.
- UI changes.

## Architecture Boundaries

Bambuddy remains the sole control plane for printer state-changing commands.
External modules must not connect directly to Bambu MQTT or FTPS. ERPNext never
controls a printer. OrcaSlicer only slices. No general arbitrary G-code endpoint
is allowed.

The legacy `/real-canary-runs` route remains only to return a blocked audit
payload. It must not construct an external adapter, make an HTTP request, or
represent a PrintFlow product integration. The blocked reason is
`external_adapter_pending_redesign`.

## Corrected Future Options

### 1. 3MF Post-Process Path

- Input `.3mf`.
- Extract the embedded plate G-code.
- Inject reviewed plate-change G-code.
- Produce a modified `.3mf` artifact.
- Send/start only through the existing Bambuddy flow.
- Verify with 3MF extraction, diff, fixture, and round-trip tests.

### 2. Bambuddy-Native Supervised Direct Command Path

- No 3MF modification.
- Operator selects exactly one printer.
- Operator confirms bed and plate state.
- Bambuddy sends one predefined allowlisted G-code sequence.
- No arbitrary G-code.
- No scheduler trigger.
- No queue auto-dispatch.
- No repeat or automatic retry.
- Audit log required.
- Hardware canary required before enabling.

Neither future path is implemented by this correction PR.
