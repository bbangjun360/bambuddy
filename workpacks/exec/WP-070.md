Implement the smallest Obico Shadow Mode baseline: synthetic Obico-like monitoring events can be received, validated, classified, recorded locally, and observed without controlling printers or changing execution state.

# Scope

In scope:

- A small explicit shadow event vocabulary.
- A default-off shadow-mode feature flag.
- Synthetic shadow-event validation and classification.
- Local shadow observation records with idempotency for repeated identical events.
- Deterministic harness/mock Obico shadow scenarios.
- Tests proving shadow observations do not create or mutate print queue, print log, printer command, scheduler, bed automation, or ERP write behavior.
- Logs/metrics that identify shadow-only results without secrets.
- A focused `test-obico-shadow` and, if useful, `harness-obico-shadow` target.

Out of scope:

- Real Obico cloud integration, tokens, webcam/image/video processing, customer data, printer credentials, Bambu MQTT/FTPS, G-code sending, printer registration, queue dispatch, queue auto-start, bed automation state changes, ERP write/posting/submission, scheduler changes, UI changes, production dependencies, destructive migrations, and any WP other than WP-070.

# Architecture Boundaries

- Bambuddy remains the sole control plane and system of record for printer commands, queue execution, print history, and bed automation policy.
- Obico Shadow Mode is observe-only. It may create shadow observations in its own local service/store but must not call `obico_actions`, `printer_manager`, `bambu_mqtt`, `bambu_ftp`, `print_scheduler`, ERP write paths, or queue/bed mutation paths.
- Shadow observations are not executable jobs and must never enqueue, pause, cancel, start, resume, or modify a print.
- Invalid payloads and timeouts are classified safely and remain side-effect-free.
- Fixtures and tests use synthetic identifiers only.

# Decisions

- Use a separate shadow-mode module instead of extending existing `obico_detection.py`, because existing upstream Obico detection can dispatch control actions.
- Use additive, in-memory local shadow records for the baseline to avoid migrations and keep rollback file-level.
- Keep the feature flag default off. Tests and harness can explicitly opt in.
- Do not add UI. Observation will be through tests, API responses, logs, and optional metrics.
- Do not read `docs/archive/FULL_SPEC_v1.1.md`; WP-070 did not explicitly request it.

# Failure and Recovery

- Duplicate events return the existing observation and status `IGNORED_DUPLICATE` without incrementing side-effect paths.
- Invalid payloads are rejected or recorded as `INVALID` without queue, printer, bed, scheduler, or ERP changes.
- Timeout/error events become `RETRYABLE_FAILURE` or safe shadow records only.
- Rollback is file-level: remove the additive shadow service/route/tests/harness target changes and remove `FARM_OBICO_SHADOW_ENABLED` from config. No migration rollback is expected.

# Risks and Human Gates

- Existing upstream Obico code can control printers when configured with pause actions. WP-070 must not reuse that path.
- Local `.env.harness` is ignored but required for isolated harness execution. It must remain `farm_wp070` with WP-070 ports while this work runs.
- No hardware/canary testing is part of WP-070. Any physical printer validation requires a later explicit human checklist.
- If conflicts later occur with WP-050, leave them for a future merge-resolution task.

# Outcomes

Implemented pending final validation. Current behavior:

- Synthetic Obico shadow events are accepted only when `FARM_OBICO_SHADOW_ENABLED=true`; default is false.
- Events are classified as `OBSERVED`, `REVIEW_RECOMMENDED`, `IGNORED_DUPLICATE`, `INVALID`, or `RETRYABLE_FAILURE`.
- All observations report `mode=SHADOW_ONLY` and no printer, queue, bed, or ERP action fields.
- Harness mock scenarios are deterministic and synthetic.
- Shadow status/metrics omit raw metadata values and did not expose the synthetic secret probe.
