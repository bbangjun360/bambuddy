# Purpose

Prepare the Bambuddy-native plate-change command transport boundary for a
future allowlisted executor without sending any real printer command.

# Current Behavior

WP-063-A added a disabled-by-default dry-run endpoint at
`POST /api/v1/plate-change/dry-run-commands` and status endpoint at
`GET /api/v1/plate-change/status`. The boundary is dry-run only, accepts exactly
one printer, requires the exact phrase
`CONFIRM_DRY_RUN_PLATE_CHANGE <printer-alias> <command-sequence>`, rejects
arbitrary command body fields, and sends no real command.

WP-063-B added allowlisted A1 mini symbolic command sequences:

- `A1_MINI_PLATE_CHANGE_DRY_RUN`
- `A1_MINI_PLATE_CHANGE_CANDIDATE_V1`

The existing service in `backend/app/services/plate_change_command.py` returns a
symbolic `command_plan` with `real_execution_supported=false`. The route in
`backend/app/api/routes/plate_change_command.py` still rejects real execution
runtime settings. The schema in `backend/app/schemas/plate_change_command.py`
forbids extra fields and exposes only enum sequence identifiers.

Existing Bambuddy live command paths were re-inspected for WP-063-C:

- `backend/app/services/bambu_mqtt.py` publishes `project_file`, stop, pause,
  resume, and `gcode_line` commands through MQTT.
- `backend/app/services/printer_manager.py` owns active MQTT clients and wraps
  print start/stop command calls.
- `backend/app/api/routes/printers.py` owns existing stop, pause, resume,
  clear-plate, bed-jog, and home-axes routes. Bed jog and home axes are typed
  route actions but still end at the generic `send_gcode()` emitter.
- `backend/app/services/print_scheduler.py` and
  `backend/app/services/background_dispatch.py` use FTPS upload before calling
  `printer_manager.start_print()`.
- `backend/app/api/routes/print_queue.py` can stop active queue items through
  `printer_manager.stop_print()` and mutates queue state.

Baseline `make verify-fast` passed on 2026-06-25 21:26 KST before edits.

# Scope

In scope:

- Add an explicit plate-change command transport interface/service boundary.
- Keep the boundary disabled, dry-run, blocked, and audit-only by default.
- Add transport result fields to dry-run records and status snapshots.
- Optionally add `GET /api/v1/plate-change/transport-status`.
- Add tests proving no real transport, MQTT, FTPS, printer manager, queue,
  scheduler, ERP, Obico, or bed automation side effect occurs.
- Add Make targets for focused transport validation if useful.
- Update WP-063 architecture and canary docs with WP-063-D prerequisites.

Out of scope:

- Real MQTT publish or printer-manager execution.
- Direct Bambu MQTT imports or command calls.
- FTPS upload, download, delete, or file dispatch.
- Raw G-code, arbitrary command text, raw MQTT payloads, or general command
  endpoints.
- Queue dispatch, scheduler dispatch, ERP submit/posting, Obico mutation,
  `BedAutomationCycle` mutation, UI work, migrations, or production
  dependencies.
- Hardware approval or physical canary execution.

# Architecture Boundaries

Bambuddy remains the only future authority for printer state-changing commands.
WP-063-C adds only a local interface shape and blocked dry-run transport result.
It must not import `BambuMQTTClient`, `printer_manager`, FTPS helpers, queue or
scheduler modules, ERP write modules, Obico mutation services, or bed automation
models from the WP-063 implementation files.

A later real executor should attach through a narrow Bambuddy-owned
`PrinterManager` method and a reviewed allowlisted client executor, not through a
route-direct MQTT client, `send_gcode()`, the scheduler, queue, background
dispatch, FTPS, PrintFlow, or SwapMod.

# Decisions

- WP-063-C does not add an execution endpoint. The safe public surface remains
  `POST /api/v1/plate-change/dry-run-commands`, `GET /api/v1/plate-change/status`,
  and read-only `GET /api/v1/plate-change/transport-status`.
- Real transport remains unsupported in this Work Package:
  `real_transport_supported=false`, `real_command_sent=false`, and
  `audit_required=true`.
- A disabled transport config family is acceptable:
  `FARM_PLATE_CHANGE_TRANSPORT_ENABLED=false`,
  `FARM_PLATE_CHANGE_ALLOW_REAL_TRANSPORT=false`, and
  `FARM_PLATE_CHANGE_TRANSPORT_DRY_RUN=true`.
- `human_approval_required=false` must not create a bypass in WP-063-C. The
  boundary remains exact-phrase gated and now blocks instead of bypassing phrase
  checks.
- WP-063-C does not approve hardware execution, sends no real printer command,
  and adds no direct MQTT, FTPS, raw G-code, queue, scheduler, ERP, Obico, or
  bed automation mutation path.

# Failure and Recovery

There is no migration or durable state. Rollback is a file-level revert of the
WP-063-C code, tests, docs, Make targets, and this ExecPlan.

Stop and revert before any hardware work if a test shows a non-zero sentinel,
an accepted raw command field, a multi-printer execution path, an approval
bypass, a direct MQTT/FTPS/printer-manager import in the WP-063 files, a
queue/scheduler/ERP/Obico/bed mutation, or any response indicating a real
command was sent.

# Risks and Human Gates

Remaining risks:

- Symbolic candidate steps remain unvalidated against A1 mini firmware.
- A local interface can make future execution easier, so tests and docs must
  keep live transport explicitly blocked.
- Dry-run success is not evidence of physical safety.

WP-063-D must be a separate Work Package before hardware execution. It requires
an exact reviewed command sequence, one named A1 mini canary with sanitized repo
alias only, physical monitoring, emergency stop/power cutoff, no automatic
retry, manual recovery, dedicated audit records, and explicit human
confirmation that this PR does not provide.

# Outcomes

WP-063-C added the Bambuddy-native local transport interface boundary in
`backend/app/services/plate_change_command.py`:

- `PlateChangeCommandTransport`
- `DryRunPlateChangeCommandTransport`
- `BlockedRealPlateChangeCommandTransport`

The public API remains safe and read-only/dry-run only:

- `POST /api/v1/plate-change/dry-run-commands` remains the safe planner.
- `GET /api/v1/plate-change/transport-status` is read-only status.
- No execute, live, send, raw, or arbitrary G-code endpoint was added.

Dry-run/status responses now report `transport_mode=DRY_RUN`,
`transport_status=BLOCKED_AUDIT_ONLY`, `real_transport_supported=false`,
`real_command_sent=false`, `audit_required=true`, and blocked reasons including
`real_transport_not_implemented` plus default blockers.

WP-063-C does not import or call Bambu MQTT, `printer_manager`, FTPS, queue or
scheduler paths, ERP, Obico, or `BedAutomationCycle` mutation paths. No direct
MQTT, FTPS, or G-code path was added, and no real printer command was sent.
Arbitrary G-code remains impossible through the schema and route design.

Future real execution must be WP-063-D. WP-063-D requires an exact reviewed
G-code/firmware command sequence, one named A1 mini, physical monitoring,
emergency stop or power cutoff, manual recovery, no automatic retry, and
explicit confirmation.
